# ECS 在公共管理与企业管理中的应用与扩展能力

> 文档用途：供公共管理、企业管理领域的专家或 Agent 评估 ECS 的适用场景、落地路径与治理要求。
> 项目地址：<https://github.com/yourblacksky/ECS>

## 一页结论

ECS 是一个本地优先、面向小模型和多设备协作的 Agent 执行内核。它不试图让一个大模型通过
超长提示词包办所有工作，而是把业务流程拆成可验证的任务、明确的能力合同、受控的执行动作
和可追踪的交接。

对公共管理和企业管理而言，ECS 的价值不在于“再提供一个聊天机器人”，而在于把自然语言
理解嵌入既有制度与流程：

- 模型负责理解诉求、提取信息、归纳材料和选择有限能力；
- 系统负责任务顺序、参数校验、权限控制、审批、失败处理和审计；
- 人负责高风险决策、例外判断、最终授权和责任承担；
- 各类业务系统通过连接器提供知识、文档、任务、审批、消息和数据能力。

这使 ECS 更适合材料密集、流程明确、需要多人协同且重视责任边界的工作，例如政策研究、
会议督办、审批材料预检、企业制度问答、经营简报和跨部门任务协同。

ECS 当前已经具备执行内核、能力注册、节点协作、关系授权、Session、Trace，以及办公流程
的定义、校验、编译、持久化和受控执行。Office Stage 会绑定 Skill 与 Connector；高风险
动作经过持久化审批，外部动作需要 Receipt 验证，失败时按合同触发补偿。真实 OA、知识库、
审批、日历、任务等系统仍需按部署单位现有技术栈接入。创建办公工单只表示流程已被编译并
保存，不代表外部业务系统已经完成动作。

## 为什么传统 Agent 难以直接进入管理流程

公共管理和企业管理通常同时具有四个特点：

1. **制度约束强**：结论必须符合现行制度、权限与办理程序；
2. **材料链条长**：信息来自会议、文件、表格、业务系统和不同责任人；
3. **协同跨度大**：一件事可能跨部门、跨层级、跨设备，甚至跨网络边界；
4. **责任要求高**：需要知道谁提供了信息、谁做了判断、谁批准了执行。

单纯依靠 Prompt 的 Agent 容易在这里暴露问题：把缺失信息自行补全、使用过期制度、越权
调用工具、在长流程中遗失上下文，或者只给出一个看似完整但无法追溯的最终答案。

ECS 的基本判断是：

> 业务流程属于系统，语言理解属于模型；高风险决定属于有责任的人。

因此，模型的自由度被放在最有价值的地方，确定性和责任边界则被工程系统承接。

## ECS 如何进入真实组织

```mermaid
flowchart LR
    A["人员提出自然语言诉求"] --> B["ECS 识别意图与所需能力"]
    B --> C["读取制度、材料与业务数据"]
    C --> D["编译为任务图与结构化交接"]
    D --> E["执行者生成中间成果"]
    E --> F["核验者检查证据与边界"]
    F --> G{"是否需要审批"}
    G -->|是| H["人工审批 / 业务系统审批"]
    G -->|否| I["受控执行"]
    H --> I
    I --> J["回执、补偿、Session 与 Trace"]
```

一个典型流程不是“一问一答”，而是：

- 明确输入、目标和办理范围；
- 将工作拆成少量、职责单一的阶段；
- 为每个阶段指定输入、输出、验收条件和失败策略；
- 在阶段之间传递结构化成果，而不是依赖模型记忆；
- 在提交、发送、删除、付款等高风险节点保留人工或策略审批；
- 保存执行路径、结果和错误，使问题能够复盘。

## 公共管理场景

### 1. 政策研究与决策参考

**实际工作**：围绕某项政策议题收集国家、地方和部门材料，识别政策变化，比较不同地区
做法，形成带来源的简报。

**ECS 可以承担**：

- 将研究主题拆分为可独立核验的问题；
- 在授权范围内检索内部知识库与公开资料；
- 保存来源、发布日期、有效期和访问范围；
- 标记证据冲突、过期材料和证据不足的结论；
- 按单位模板生成研究简报，提交人工复核。

**治理重点**：政策版本、生效日期、引用可追溯、内部与公开材料分区、最终判断由业务人员
负责。

### 2. 会议纪要与督查督办

**实际工作**：从会议材料或转写中提取决定事项、责任部门、责任人、完成时限和待确认问题，
复核后形成任务与提醒。

**ECS 可以承担**：

- 从原始材料中提取事实，不推测会议没有形成的决定；
- 对人名、日期、责任归属逐项回查原文；
- 把核验后的行动项写入任务或督办系统；
- 创建跟进日程并通知相关人员；
- 保存创建结果和失败回执，必要时撤销已创建事项。

**治理重点**：涉及责任分配时必须核验；未明确责任人或期限的事项应进入待确认状态，而
不是由模型自行决定。

### 3. 行政审批材料预检

**实际工作**：申请人在正式提交前，需要判断办理类型、材料完整性、金额或条件限制、审批
路径与例外事项。

**ECS 可以承担**：

- 根据事项类型生成材料清单；
- 对照当前有效制度检查必填项、额度和附件；
- 将缺失材料、制度例外和敏感信息单独列出；
- 生成审批说明与附件目录；
- 在人工复核并授权后调用审批系统，保存业务回执。

**治理重点**：ECS 适合作为预检和编排层，不应替代法定审批主体；制度检索必须带版本，
提交动作必须使用独立授权。

### 4. 公共服务事项辅助办理

**实际工作**：群众或基层工作人员用自然语言描述诉求，系统需要识别可能事项、解释材料
要求，并把请求路由到正确渠道。

**ECS 可以承担**：

- 将自然语言诉求映射到有限事项与知识范围；
- 给出材料清单、办理入口和需要人工确认的问题；
- 调用确定性的日期、文本、表单校验等工具；
- 在不同终端之间协作，例如窗口电脑处理材料、移动端提供定位或通知；
- 对无法确认的事项明确失败或转人工。

**治理重点**：不把建议包装为正式行政决定；涉及个人信息时执行数据最小化、目的限制和
留存策略。

### 5. 应急协同与现场信息汇总

**实际工作**：多个现场或部门分别上报信息，需要并行收集、交叉核对并形成统一态势。

**ECS 可以承担**：

- 通过节点组让多个授权节点分别返回本地事实；
- 使用 `broadcast` 收集多方结果，或使用 `race` 获取首个可用结果；
- 保留每个节点的原始结果，再进行汇总；
- 调用移动端定位、通知、提示音等真实设备能力；
- 使用 Trace 记录请求经过的节点和失败位置。

**治理重点**：当前节点组与递归汇总的核验链仍需加强；高影响态势判断不能仅依赖自动汇总，
移动端也不应被视为永久在线的后台执行器。

## 企业管理场景

### 1. 企业制度问答与合规预检

ECS 可将员工问题限制在经过授权的制度范围内，检索当前版本，给出引用，并将例外情况送交
合规人员。它还可以把“查询制度”“检查材料”“形成意见”“人工复核”拆成不同阶段，避免
模型在一次回答中同时扮演申请人、审核人和批准人。

### 2. 采购、费用与合同前置检查

在连接采购、财务、合同模板和审批系统后，ECS 可检查金额、必备附件、供应商材料、审批
路径和例外条款，生成待提交材料包。实际提交仍受 Scope、能力白名单和人工审批约束。

### 3. 经营分析与管理简报

通过数据库、ERP、CRM、表格和文档连接器，ECS 可以将一个经营问题拆成数据提取、指标
计算、异常解释、事实复核和简报生成。确定性指标计算交给工具，模型只负责语言理解和有限
解释，减少“模型算错但表达得很确定”的风险。

### 4. 跨部门项目协同

ECS 可以把项目例会、行动项、日程、消息和文档串成办公工单；每个阶段有明确负责人、前置
依赖、交付物和验收条件。失败时可以暂停、重试或触发补偿，而不是让一个对话无限继续。

### 5. 一线设备与后台能力协同

桌面、服务器、Android、iOS 和浏览器节点可以发布不同能力。例如，服务器访问内部数据，
桌面节点生成人工可读结果，手机提供定位、通知或现场反馈。ECS 不假设所有终端能力相同；
权限关闭或硬件不可用时，能力会从候选集合消失。

### 6. 私有化的内部助手

ECS 可以连接本地 Ollama 和小模型，在组织控制的设备或网络中运行。对于不能直接发送到
外部云模型的材料，可优先在本地完成分类、提取、路由和确定性处理，再按单位策略决定是否
调用其他模型或系统。

## 已具备、需接入与尚待补齐

### 已具备的工程基础

- 本地优先的 Go 执行内核和 OpenAI-compatible 模型接口；
- Tool、Skill、Agent、Pipeline 的分层能力模型；
- 结构化参数校验、工具超时、输出限制和高风险审批模式；
- 单节点执行、节点组执行和有深度限制的递归协作；
- 节点发现、加入申请、配对批准、租约和关系凭证；
- 按 Scope、Tool、Skill、Group 收窄的节点授权；
- Session 连续上下文与树状 Trace；
- 桌面、Android、iOS 和浏览器宿主；
- 办公组件的清单校验、连接器就绪检查、任务图编译、Handoff 和工单持久化；
- Office Stage → Skill → Connector 执行合同、持久化人工审批、Receipt 验证与补偿；
- AgentTeams Task 与 Office Stage 的归属、状态和 Trace 映射；
- 会议跟进、研究简报、审批材料三个办公组件示例。

### 需要按组织接入的能力

- 统一身份、组织架构、租户和单点登录；
- OA、审批、任务、日历、邮件、即时消息和通讯录；
- 文档、表格、PDF、OCR、文件库、模板和电子签名；
- 带 ACL、版本、引用和有效期的知识检索；
- ERP、CRM、财务、采购、合同、数据库和内部 API；
- 数据分级、DLP、密钥管理、长期审计和合规留存。

连接器可由本地 Tool、HTTP API、Webhook 或 MCP 网关实现。ECS 通过能力名称而不是厂商
名称依赖连接器，例如 `office.knowledge.search`、`office.document.write` 和
`office.approval.submit`，因此可以适配不同单位的技术环境。

### 生产化前尚待补齐或验证

- 内建 TLS / mTLS、跨节点请求签名和外部工具的操作系统级沙箱；
- Session 的 TTL、隐私删除接口和更完整的数据生命周期管理；
- 离线队列、死信队列、断点恢复和流式输出；
- 节点组及递归汇总与单节点一致的完整验证链；
- 关系授权、跨节点策略和 AgentTeams 归属的一致性；
- 针对具体行业法规、等保要求和单位安全制度的部署验证。

这些边界决定了 ECS 当前更适合受控试点、内部辅助和人机协同流程，而不是未经二次建设就
直接承担法定决定、资金支付或关键生产控制。

## 扩展模型

ECS 的扩展不是给系统继续堆叠 Prompt，而是选择合适的工程层：

| 扩展对象 | 解决的问题 | 管理领域示例 |
|---|---|---|
| Tool | 一个确定性动作 | 查询制度、计算指标、创建任务、提交审批 |
| Skill | 何时及如何使用一组能力 | 制度核对、会议事实提取、材料完整性检查 |
| Agent | 一个职责单一的角色 | 规划员、执行员、事实核验员、合规复核员 |
| Pipeline | Agent 的执行路径 | 规划 → 执行 → 核验 |
| Office Component | 可复用的业务流程 | 会议督办、政策研究、采购审批 |
| Platform Host | 操作系统或设备能力 | 定位、通知、扫码、现场采集 |
| Discovery Provider | 节点如何被找到 | 局域网发现、私有 Registry |

一个新的管理流程通常可按以下方式建模：

1. 定义办理意图、输入字段和禁止猜测的信息；
2. 划分角色与阶段，明确依赖关系；
3. 为每个阶段定义输入成果、输出成果和验收条件；
4. 声明所需连接器及最小操作范围；
5. 标记数据级别、允许去向、留存和审计要求；
6. 指定失败时暂停、重试、终止还是补偿；
7. 在高风险动作前设置人工或策略审批；
8. 用真实样本进行回归测试，再逐步扩大授权范围。

## 三种推荐部署形态

### 形态 A：单机辅助

一个 ECS 节点连接本地模型和少量内部工具，用于材料整理、制度检索、文本处理和个人工作
流。适合低成本验证交互方式、模型能力和数据边界。

### 形态 B：部门能力节点

各部门维护自己的 ECS 节点和能力白名单。例如，法规部门提供制度检索，财务部门提供指标
查询，办公室提供会议和督办连接器。节点之间可以发现对方，但只有经过审批的关系和 Scope
才能执行能力。

### 形态 C：跨终端协作网络

服务器承担稳定计算与业务系统接入，桌面承担人工复核，移动端提供现场能力，浏览器作为
临时受限叶子。拓扑可以动态变化，但权限不会沿调用链自动继承。

无论采用哪种形态，跨机器部署都应由 HTTPS、Tailscale、WireGuard 或单位现有零信任网络
提供安全传输；发现服务不能被当作信任中心。

## 建议的试点方法

首个试点应选择“高频、材料密集、规则相对明确、允许人工复核、错误可恢复”的流程。会议
跟进或研究简报通常比自动审批更适合作为第一阶段。

### 第一阶段：影子运行

- ECS 只生成建议和结构化工单，不写入正式系统；
- 使用历史脱敏样本和真实人员结果进行对照；
- 观察事实准确率、材料完整率、人工修改率和失败类型。

### 第二阶段：低风险写入

- 接入文档草稿、个人任务或测试日历；
- 使用最小 Scope 和能力白名单；
- 每个写操作保存回执，并验证撤销或补偿能力。

### 第三阶段：受控业务流程

- 接入正式知识库和业务系统；
- 高风险节点保留人工批准；
- 纳入身份、数据分级、DLP、监控、留存和应急机制；
- 定期回归制度版本、连接器权限和跨节点策略。

建议的评估指标包括：处理时长、人工修改率、事实可追溯率、缺失材料发现率、越权调用数、
失败可见率、补偿成功率，以及使用者是否理解系统给出的边界。

## 希望领域专家或 Agent 重点评估的问题

1. 哪些公共管理或企业管理流程最符合“高频、规则明确、可人工复核、错误可恢复”的条件？
2. 哪些环节可以由模型辅助，哪些环节必须由确定性规则或有责任的人完成？
3. 现有三个组件——会议跟进、研究简报、审批材料——还缺少哪些真实角色、材料或例外路径？
4. 公共管理场景中的法定权限、档案留存、个人信息和跨部门共享应如何转化为可执行策略？
5. 企业场景中最值得优先接入的是知识库、OA、ERP、CRM，还是任务与通讯系统？
6. 应使用哪些业务指标证明系统真正改善了管理质量，而不只是提高了文本生成速度？
7. 哪些失败必须“暂停并转人工”，哪些可以安全重试，哪些需要自动补偿？
8. 如果选择一个 4–8 周试点，合适的流程、数据范围、参与角色和验收标准是什么？

## ECS 的定位

ECS 的定位是组织中的“可信执行层”，不是新的万能决策者。

模型可以参与现实工作，但能力必须可声明，权限必须能收窄，流程、失败和结果必须能检查。
对公共管理和企业管理而言，系统不仅要完成任务，还要说明依据来自哪里、谁允许了执行，
以及出现问题后如何停止和恢复。
